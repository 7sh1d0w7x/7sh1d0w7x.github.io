What an evidence pack looks like

2026-10-30 · artifact example · one disposable lab VM

The question

A server hardening assessment answers one question, in plain terms: is this machine actually set up the way everyone assumes it is?

Not “is it secure” — nobody can answer that from a scan. The narrower question is answerable: which logins are allowed, what is listening, who can become root, which rules are actually loaded, how far behind the box is on updates. Each of those has a yes/no answer you can verify.

What you receive

1. a short written report  ... what was found, what matters first, what to do
2. the raw evidence ....... the command output behind every line of that report
3. before and after ....... the same checks run twice, plus the difference
4. a checksum manifest .... so the files can be compared later

The report is what you read. The evidence is what makes the report checkable instead of trusted — you, or anyone you hire later, can re-run the same checks and compare.

What you actually get depends on the job. An assessment-only engagement produces the report and the raw evidence. The before/after pair only exists where changes were agreed in writing and made; a single pack is what an assessment produces.

The 11 checks, and what they are not

All read-only. Nothing on the host is modified and no packages are installed. On a small VM the whole run takes about ten seconds.

01  host identity ......... hostname, kernel, OS, uptime
02  sshd effective ........ permitrootlogin, passwordauth, maxauthtries, x11, allowusers
03  sshd drop-ins ......... the files in /etc/ssh/sshd_config.d
04  listening sockets ..... what the box has open, as seen from the box
05  kernel sysctl ......... rp_filter, kptr_restrict, syncookies, ptrace_scope
06  firewall policy ....... nft / ufw / firewalld, or the absence of all three
07  sudo access ........... what each privileged user may run
08  uid 0 accounts ........ who is root besides root
09  SUID binaries ......... the setuid surface
10  cron .................. root crontab and /etc/cron.d
11  pending updates ....... how far behind the box is

This is a limited assessment, not an exhaustive audit. It covers configuration surface, not application logic, not code review, not network scanning, and not whether a specific CVE affects you. Eleven checks are chosen because they answer the questions above cheaply and reproducibly — not because they are everything.

One host, before and after

The example below is a throwaway lab VM (Ubuntu 26.04, KVM), not a client. Both packs come from the same day: 17:37 and 22:33, about five hours apart.

Check                        before                after
─────────────────────────────────────────────────────────────
permitrootlogin              no                    no
passwordauthentication       yes                   yes
maxauthtries                 3                     3
x11forwarding                no                    no
allowusers                   lab                   lab
public listeners (LISTEN)    4                     4
firewall policy              niciun ruleset   →    drop
uid 0 accounts               root                  root
SUID binaries                15                    15
pending updates              23                →    0

Two rows changed out of ten. The other eight were already correct before the work started, and the pack shows that rather than hiding it — a before/after table where everything improved would mean the “before” was chosen for effect.

Checksums: what they do and do not prove

Every file is hashed when the pack is created, and the hashes are listed in SHA256SUMS (14 entries — the manifest does not hash itself).

$ sha256sum -c SHA256SUMS
00-meta.txt: OK
01-host.txt: OK
02-sshd-effective.txt: OK
...
transcript.txt: OK

What that gives you: if a file changes and the manifest does not, the mismatch shows up — accidental edits and careless repackaging get caught. What it does not give you: proof of origin, of when it was collected, or that the commands were run as described. Someone who alters a whole pack can recompute every hash in it. The manifest makes silent single-file edits visible; it is not a signature and it is not a timestamp.

What is not collected

✗ private keys, password hashes, tokens or credentials
✗ file contents from your home directory or application data
✗ packet captures or traffic logs
✗ anything that needs write access to the host

This example is a scratch VM: its hostname (lab), its user and its loopback addresses are not anyone's server. I checked the archive for credentials and external addresses before publishing it — the only addresses in it are 127.x and wildcard binds. That check is not a guarantee for any other host; it is what was verified for this file.

Limits of this example

· the state shown is the end of one hardening session, not a fully
  hardened production baseline — deferred items stayed deferred
· sshd -T reports the configuration the daemon evaluates; it is not
  on its own proof that the running process was reloaded
· ss -tulpn lists sockets bound on the host; it does not prove what is
  reachable from the internet (that needs a scan from outside)
· listing the drop-in files does not show their contents
· 11 checks are a limited assessment, not an exhaustive audit
· only the after pack is published: the before pack exists but is not
  downloadable, so the diff above cannot be re-derived from this page
· one VM, one distribution, one day
