The file is not the configuration

2026-10-18 · Linux hardening · 4 min read

One question about one host: is password authentication on for SSH? Not a hard question. It has a yes/no answer, it is written down somewhere, and the host knows it.

It took four files to answer it. And I never wrote one of them.

What I read first

Open the obvious file, find the obvious line:

$ sed -n 65p /etc/ssh/sshd_config
#PasswordAuthentication yes

It is commented out. So the file declares nothing, the compiled default applies, and the default is… yes. Fine. Question answered, right?

No. Because "commented out" only tells you what this file says. It says nothing about what else is in the chain.

What the host actually does

$ sshd -T | grep -i '^passwordauthentication'
passwordauthentication yes

Enabled. But sshd -T does not tell you why — whether that is the default, or something set it. So: which file decided?

Where it comes from

/etc/ssh/sshd_config
  └ Include /etc/ssh/sshd_config.d/*.conf
    └ 40-redhat-crypto-policies.conf
      └ Include /etc/crypto-policies/back-ends/opensshserver.config

Four files. The second is a glob — any file dropped into that directory joins the configuration, and nothing in the main file hints at what is in there. The fourth is generated by the crypto-policies subsystem: not a file you edit, a file the system writes.

On this host, the value turned out to be the compiled default — nothing in the chain overrode it. But you cannot know that without reading the whole chain, and the chain has a wildcard in the middle and a generated file at the end.

The glob cuts both ways

A glob is a promise and a trap. Two cases, same directory, two evenings apart.

$ sudo ls -l /etc/ssh/sshd_config.d/
-rw-r--r-- 1 root root 17  00-hardening.conf
-rw-r--r-- 1 root root 17  '00=hardening.conf'    ← read anyway

The second file was a typo: = where a - belonged. It matched *.conf, so sshd read it, and sshd -T showed values from a file that cat on the expected path did not reveal. Two drop-ins were in force at the same time, and only one of them was in my head.

$ sudo ls -l /etc/ssh/sshd_config.d/
-rw-r--r-- 1 root root 47  00-hardening.conf
-rw-r--r-- 1 root root 44  00-hardening.conf.bak   ← never read

The opposite happens just as often. A backup copy left in the same directory looks like broken configuration and is silently ignored: no warning, no error, nothing in the log. It behaves like an empty file while looking like a problem.

So the check is not “does this file end in .conf”. It is “which files match the glob this host actually uses”:

$ grep -n '^Include' /etc/ssh/sshd_config
24:Include /etc/ssh/sshd_config.d/*.conf

Here the glob is *.conf, so 00=hardening.conf counted and 00-hardening.conf.bak did not. On another host the include line can read differently, or be missing — in which case the whole directory is decoration and your careful edits do nothing.

Why this matters more than it sounds

Because it turns a sentence you have probably said into one you cannot support:

“I read the config.” Which config? The file you opened, or the configuration the daemon resolved — which is that file plus every file it includes, recursively, plus whatever the distro generates into it?

And it is worse on an immutable host. On Fedora Atomic, Bazzite or a bootc image, the effective file is a three-way merge of /usr/etc → /etc, so the file you are reading may not even be the one that wins. The old advice — “check the config file” — quietly stopped being true.

What to do instead

Ask the two questions separately, and never accept an answer to only one of them:

1. what is ENFORCED right now?      sshd -T · sysctl -n · nft list ruleset
                                    systemctl show · /proc · live sockets
2. which file and line SET it?      follow the includes, recursively,
                                    and say when the answer is "the default"

That is the entire idea behind state-witness, the tool I have been building: read the resolved runtime state, and report the provenance — including when the honest answer is “nobody set this, it is the compiled default”.

The takeaway

A finding without provenance is a claim. A finding with provenance is evidence — you can re-run it, and it either reproduces or it doesn't. “Password authentication is enabled” is a claim. “Password authentication is enabled, and here is the chain that resolves to that” is something you can check.

Four files to answer one question is not a flaw in the host. It is how Linux configuration has always worked. The flaw is pretending otherwise.
