SSH host key changed: when to accept it, and when to stop

2026-10-20 · Linux hardening · 5 min read

This is what I got when I reconnected to a container I had just recreated:

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!
It is also possible that a host key has just been changed.
The fingerprint for the ED25519 key sent by the remote host is
SHA256:R8PZd9wIg8Bb5Y1Ts5Nmr8tF29TrWwpY8fSYRf5AJaU.
Offending ECDSA key in /home/user/.ssh/known_hosts:12
Host key for [127.0.0.1]:2222 has changed and you have requested strict checking.
Host key verification failed.

One detail in that message looks like a contradiction: it names an ED25519 fingerprint, then an ECDSA entry in known_hosts. It is not a contradiction — the stored entry was ECDSA, the server now offers ED25519. Same host and port, different key: that is exactly the change the check is reporting.

The honest reaction is to press yes and move on. That is also how people get owned. This post is the ten minutes I spent instead, and the rule I came out with.

What a host key is

Every SSH server has its own key pair, generated once when SSH is installed or first started. It works the same way as your own key pair, only backwards:

your key pair ...... proves who YOU are, to the server
the host key ....... proves who the SERVER is, to you

Without it, you would have no way to tell the server you meant from anything that answered on that address.

Why your machine remembers it

The first time you connect, your client receives the server's public key and stores the key itself in ~/.ssh/known_hosts. The fingerprint you see in the warning is not a separate record — it is a short, comparable form derived from that key, so you can check it by eye or read it over the phone. On every later connection, it compares what it gets now with what it stored:

same key ..... continue, silently
other key .... stop, and show the warning above

That warning is not a bug. It is the only signal you have that you might be talking to something else.

The detail that trips everyone: [host]:port

My entry was not stored under 127.0.0.1. It was stored under [127.0.0.1]:2222, because the port is not 22. That is why the obvious fix does nothing:

ssh-keygen -R 127.0.0.1              # does not touch the entry
ssh-keygen -R "[127.0.0.1]:2222"     # removes it

The brackets are not decoration. They tell the client "this is host and port, not a hostname". If you have ever "fixed" the warning and had it come back, this is why.

Two situations, one question

A changed key has two possible explanations, and they are not equally common. Everything else — a reinstall, a migration, an ephemeral container — is a variant of the first:

legitimate ..... you reinstalled the server, recreated the container,
                 migrated to a new provider, or the provider rotated the keys

hostile ........ someone is between you and the server, presenting their key

The question that separates them is not technical. It is:

Did I change anything?

If yes — a reinstall, a new container, a migration — you know why the key differs, and you can verify the new fingerprint through a channel you trust. If no, stop. Not "probably fine". Stop.

What I did

I had recreated the container two minutes earlier, so I knew the key would differ. That is the only reason the next step was safe:

ssh-keygen -R "[127.0.0.1]:2222"

The next connection asked me to trust a new key. I compared the fingerprint with the one the setup script had printed:

SHA256:R8PZd9wIg8Bb5Y1Ts5Nmr8tF29TrWwpY8fSYRf5AJaU   ← matches the script output

Then I accepted. Two conditions, both checked: I knew why it changed, and I had an independent source for the new value. Without both, "yes" is a guess.

On a server you do not control

This is where it gets less comfortable. You cannot re-run a setup script you did not write. In order of preference:

  1. The provider's console. Check whether your panel shows the host keys. If it does not, open the serial or VNC console and read /etc/ssh/ssh_host_ed25519_key.pub in there yourself.
  2. A second channel. Ask the person who runs it, over something that is not the connection in question.
  3. Nothing. If you cannot verify it, do not accept it. A failed connection costs you five minutes; a wrong "yes" costs you the server.

Why StrictHostKeyChecking=no is a bad habit

You will find this suggested in tutorials and CI snippets, usually to make a script stop complaining:

ssh -o StrictHostKeyChecking=no ...

What it does is turn off exactly the check that just protected you. The warning disappears, and so does the only signal that would tell you something is wrong. If you need it for automation, the safer shape is to pin the expected key instead of disabling the check — but that is a different post.

The rule

A changed host key is not an error to suppress. It is a question: do I know why this changed, and can I verify the new value somewhere else?

Two yeses — accept, and move on. Anything else — stop. The wall of @@@ is not the tool being dramatic. It is the tool doing its one job.
