Lynis said 65. Then the reboot said 69.

2026-10-30 · Linux hardening · 6 min read

I ran a hardening pass on a lab VM and watched the score go 65 → 70 → 69 → 72 → 74.

The interesting number is the 69. That is the one where the score went down after I fixed things, and it is the only part of the sequence I would trust in a report.

The starting point

The VM was not fresh. Six earlier fixes were already applied: root login off, X11 forwarding off, an AllowUsers line, MaxAuthTries 3. Baseline:

Hardening index : 65 [#############       ]
Tests performed : 256
Suggestions     : 43
Warnings        : 0

Zero warnings and forty-three suggestions is a specific kind of result: nothing is actively wrong, a lot is merely undone. That is the normal state of a server someone has been maintaining without a checklist.

First fix: SSH, seven settings, one refusal

Seven of the suggestions pointed at sshd. I did not copy them.

LogLevel VERBOSE            # logs the key fingerprint at login
MaxSessions 2               # one compromised channel does not open ten
AllowTcpForwarding no       # the box stops being a tunnel
AllowAgentForwarding no     # your agent cannot be hijacked here
ClientAliveInterval 300     # without this, TCPKeepAlive no
ClientAliveCountMax 2       # leaves dead sessions hanging
TCPKeepAlive no

The last two are a pair. Lynis suggests both, and applied alone TCPKeepAlive no is worse than doing nothing: with ClientAliveInterval 0 there is nothing left to detect a dead peer, so stale sessions sit in the process table. A checklist is not a plan.

The one I refused: move SSH off port 22. It does not reduce risk. It moves noise out of your logs and hides the same attack from yourself. It is written in the report as a decision, not skipped quietly.

65 → 70

Then the reboot

Twenty-three pending updates, a kernel bump, one reboot. The score came back 69.

One new suggestion had appeared:

FIRE-4590  Configure a firewall/packet filter
firewall_active=0   firewall_installed=0   firewall_empty_ruleset=1

Before the reboot, Lynis saw a firewall. After it, nothing. Nothing had degraded — the score simply stopped believing something that was never true. Whatever rules existed were in memory, and memory does not survive a restart.

A score that goes down after a reboot is more useful than one that only goes up. It means the tool noticed. The dangerous version of this exercise is the one where you fix ten things, never reboot, and ship a report describing a machine that will not exist tomorrow morning.

The evidence that is not a score

I applied a default-deny ruleset with nftables, and this time I armed the undo before applying it:

nft -c -f /etc/nftables.conf                      # syntax check, free
systemd-run --on-active=180 --unit=nft-rollback \
  /bin/sh -c 'nft flush ruleset; systemctl disable --now nftables'
systemctl enable --now nftables
# then: open a NEW ssh session, and only if it works
systemctl stop nft-rollback.timer

Three minutes to lose SSH is three minutes you get back for free. Without that, a typo in a policy line is a console trip to a machine you may not have physical access to.

Here is the part I would put in front of a client, because it needs no trust in any scanner:

from another host, against that machine:

port 22   → open (8 ms)
port 8080 → timeout after 5 s      ← DROP, not REFUSE
port 3306 → timeout after 5 s      ← DROP, not REFUSE

A closed port on a host without a firewall answers instantly with a TCP reset: “connection refused.” Here it goes silent. That silence is the signature of policy drop, and it is visible from the outside. A scanner score is a number you have to believe; a dropped packet is a fact you can reproduce.

Where scores plateau, and why

Then the last round: banner, login.defs (umask, password age), four unused kernel protocols blacklisted, fail2ban. Suggestions dropped 43 → 26. The score moved 72 → 74.

Most of that work removed suggestions without moving the number much, because the index is:

hardening_index = points × 100 / total_points

Every test has a fixed maximum, and tests are not weighted equally. Fixing twelve low-weight items earns less than one heavy one. So the last few points are not more work — they are different work: auditd, file integrity monitoring, remote logging. Those are the things I would price separately instead of bundling into a cheap audit and doing badly.

Two traps worth stealing

1. sudo tee file <<'EOF'
   sudo reads its password from stdin. Your heredoc is stdin.
   The first line of your config becomes a password attempt,
   tee writes nothing, and the error goes to stderr you scroll past.
   Fix: sudo -v first, then the heredoc.

2. systemctl restart fail2ban && fail2ban-client status sshd
   Too fast. The client asks for a socket the server has not created yet.
   “Failed to access socket” is a race, not a broken service.

What I refused, and why that is the product

Eight suggestions stayed refused on purpose:

Port 22              theatre, not risk
GRUB password        lockout risk at boot, for little gain
/home /var separate  a reinstall, not an audit finding
SHA_CRYPT rounds     outdated: this system uses YESCRYPT
USB storage off      irrelevant on a VM, a policy call on a laptop
malware scanner      poor cost/benefit on a server, offer it separately
auditd, AIDE         the next level, priced separately
remote logging       needs a second host to mean anything

Anyone can run a scanner and paste its output. What a client is paying for is the paragraph next to each finding that says do this, skip that, and here is the reason. The refusals are where the judgement shows — and they are also where a report stops being copy-pasteable from a blog post.

The takeaway

If you are going to run a hardening benchmark, run it three times: before, after, and after a reboot. The third run is the only one describing the machine you will actually have. And keep the raw output of all three — not because the score matters, but because the diff is the only claim you can defend six months later when someone asks what changed.
