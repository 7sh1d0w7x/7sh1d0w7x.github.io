What a hardening report actually looks like (real example)

2026-10-14 · Linux hardening · 6 min read

Most "server hardening" is sold as a list of advice. Disable root login. Use keys. Set up a firewall. That list is free on the internet — you don't need to pay anyone for it.

What you actually pay for is evidence: proof that a specific setting on a specific machine was checked, changed, and verified. So here's the report a client gets from me, filled in with a real (sanitized) example. No pitch. Just the document.

The shape of it

1. SUMMARY          what was at risk, what's closed now
2. METHOD           what was checked, with which command
3. BEFORE / AFTER   table: setting · old value · new value · why
4. EVIDENCE         raw output, not claims
5. WHAT STAYED OPEN what wasn't fixed, and why
6. RECOMMENDATIONS  next steps, optional

Section 5 is the one almost nobody includes. Keep reading — it's the reason the rest is trustworthy.

The example: a 2-core VPS running n8n

Small box, one purpose, exposed to the internet. Client asked: "is this thing safe enough to leave running?" Here's the summary section, verbatim:

BEFORE: SSH accepted passwords (brute-forceable), root login
        allowed with a password, X11 forwarding on, no firewall
        rules persisted, backup existed but had never been restored.

AFTER:  SSH keys only, root login disabled, X11 forwarding off,
        nftables default-deny with 2 ports open, backup restored
        and timed in an isolated environment.

CLOSED: 4 risks (2 high, 1 medium, 1 low)
OPEN:   2 (see section 5)

Before / after, with reasons

The table is the core of the report, because "why" is what separates a change from a guess.

SETTING                    BEFORE              AFTER        WHY
PasswordAuthentication     yes                 no           password auth is
                                                             brute-forceable at
                                                             internet scale
PermitRootLogin            without-password    no           removes a
                                                             well-known target
X11Forwarding              yes                 no           X11 forwarding
                                                             exposes a data
                                                             channel + display
MaxAuthTries               6                   3            limits attempts
                                                             per connection
nftables                   not persisted       default-deny only 22+443
                                                             open

Evidence (raw output, not claims)

Every line in the table above has an output behind it. This is what gets attached:

$ sshd -T | grep -iE "passwordauth|permitroot|x11forwarding"
passwordauthentication no
permitrootlogin no
x11forwarding no

$ nft list ruleset | head -6
table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;

Note the first command. That command doesn't read the config file. It asks the running daemon what it really applies. That distinction matters more than it sounds, and it's the trap in the next section.

The trap that ate an hour

This one is worth publishing because it's the kind of thing that makes a "hardened" server not actually hardened.

I edited /etc/ssh/sshd_config correctly. The setting was there, uncommented, saved. And sshd -T still reported the old value.

The reason: modern distros include a drop-in directory near the top of the main config —

Include /etc/ssh/sshd_config.d/*.conf

— and in OpenSSH, the first value obtained wins. Drop-ins are read before the rest of the file, so a distro-shipped drop-in was overriding my edit. The fix isn't to edit harder; it's to put your setting where it's read first:

/etc/ssh/sshd_config.d/10-hardening.conf
    X11Forwarding no

Lower number, read earlier, wins. Lesson: what's written is not what's applied. Always verify against the running service, never against the file.

Section 5: what stayed open

Here's the part that builds more trust than any success claim:

1. No intrusion detection (auditd/AIDE) — out of scope for this
   engagement; monitoring is a separate service.
2. Backup restore was tested manually, not automated — the client
   should schedule a quarterly restore test.

A report with zero open items can't be checked, so you have no reason to trust it. A report that names exactly what's still open is checkable, and that's why it can be trusted.

How to judge anyone selling you this

If you're shopping for hardening (from me or anyone else), ask for three things:

1. BEFORE / AFTER with the reason per setting — not a generic checklist
2. RAW OUTPUT as evidence — not screenshots of a tool's green ticks
3. WHAT STAYED OPEN — a report with zero open items is hiding something

If a vendor can't produce those three, you're buying advice you could have found for free.

The honest part

This example is sanitized — hostname, IPs and client details are changed, and the values are from a lab box I run for exactly this purpose. But the structure, the commands, and the trap are real: the drop-in override above cost me an hour and is now written into the runbook so it doesn't cost the next one.

That's the whole point of doing the work in a lab before touching a client's box. The mistakes are free there.
